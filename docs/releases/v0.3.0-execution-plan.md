# GoldenPath v0.3.0 Execution Plan

## Status

**Planned release:** v0.3.0  
**Theme:** Operational Paved Road & Real-Environment Assurance  
**Tracking epic:** #111  
**Execution phases:** #112 through #118  
**Evidence boundary:** repository/reference evidence, supported ephemeral-runtime evidence, and evidence from one explicitly identified real non-production environment. Production validation remains a separate claim and is **NOT CLAIMED** by this release.

GoldenPath v0.3.0 is not a claim of infallibility, universal cloud support, or production certification. Its purpose is to prove that GoldenPath can bootstrap, discover, continuously verify, degrade, recover, and re-qualify one supported real non-production platform environment while preserving strict identity and evidence boundaries.

## Release thesis

GoldenPath v0.1.0 established a repository/reference baseline with deterministic risk-adaptive assurance, fail-closed evidence semantics, policy as code, immutable promotion, supply-chain controls, and explicit separation between repository, runtime, and production claims.

GoldenPath v0.2.0 added a reproducible Kubernetes Runtime Lab, signed identity-bound runtime assurance receipts, continuous assurance, recovery/re-verification semantics, a coherent CLI, and exact-candidate self-qualification.

v0.3.0 moves the project one level higher:

```text
Intent
  -> Risk
  -> Assurance Plan
  -> Governed Environment Bootstrap
  -> Desired State
  -> Real Cloud / Kubernetes Environment
  -> Independent Discovery
  -> Observed Environment Snapshot
  -> Platform Drift Analysis
  -> Dependency / Identity Graph
  -> Assurance Receipt
  -> Resilience Exercise
  -> Recovery
  -> Fresh Re-verification
  -> Tamper-Evident Assurance History
```

The release must prove this chain against one explicitly supported real non-production environment without weakening the existing fail-closed or claim-tier rules.

## Why v0.3.0 exists

The v0.2.0 Runtime Lab proves that GoldenPath can exercise assurance contracts against a real Kubernetes API in an isolated disposable environment. That is intentionally not equivalent to operating a real cloud platform.

The next maturity gap is operational truth:

- real cloud identity;
- real remote state;
- a real managed or otherwise explicitly selected Kubernetes target;
- real registry identity;
- real GitOps reconciliation;
- real DNS/TLS and secret integration where required by the supported lane;
- real observability APIs;
- independently discovered state;
- drift across platform dependencies;
- bounded failure and recovery evidence.

v0.3.0 closes that gap for one controlled non-production lane.

## Core release invariants

These constraints apply to every phase and may not be weakened for implementation convenience.

1. **Fail closed.** Missing, malformed, stale, contradictory, unsupported, unverifiable, permission-denied, or identity-mismatched required evidence must not produce PASS.
2. **Evidence tiers remain distinct.** Repository/reference, ephemeral runtime, real non-production environment, and production validation are separate claim classes.
3. **Non-production is not production.** A real cloud account or cluster does not authorize a production claim.
4. **Exact identity binding is mandatory.** Evidence must bind to the exact source revision, artifact digest, desired-state revision, applicable assurance/policy plan, environment identity, cluster/runtime identity, and execution identity where relevant.
5. **Observed state outranks self-declaration.** A generated file, Terraform output, Helm render, or GitOps manifest cannot substitute for authoritative discovery when the claim is about the running environment.
6. **Build once, promote immutable artifacts.** Artifact identity remains digest-based.
7. **GitOps remains desired-state authority.** Bootstrap actions must be explicit and bounded; steady-state hidden mutation is not allowed.
8. **Unknown is not PASS.** Unreachable, unauthorized, unsupported, or ambiguous authoritative sources must remain explicit.
9. **Historical PASS never overrides current failure.** Assurance is stateful in time but current state is authoritative.
10. **Recovery requires fresh evidence.** A recovered target does not return to VERIFIED until required controls are re-observed and re-verified.
11. **Resilience exercises are bounded.** Exercises must be allowlisted, reversible, identity-bound, and refused against production by default.
12. **Graph relationships require evidence.** GoldenPath must not fabricate dependencies to make explainability appear complete.
13. **Ledger claims are conservative.** A tamper-evident chain does not imply an immutable backing store unless that property is independently proven.
14. **Human boundaries remain explicit.** Automation must not silently cross approval, ownership, or production-control boundaries.
15. **GoldenPath qualifies GoldenPath.** The exact v0.3.0 release candidate must pass the supported repository, runtime, and real-environment qualification path.

## Evidence model

v0.3.0 extends the practical claim model without redefining previous evidence meanings.

| Tier | Meaning | Example evidence | May claim production? |
|---|---|---|---|
| Repository/reference | Static, generated, fixture, CI, policy, architecture, supply-chain, or desired-state evidence | schema validation, policy tests, provenance verification | No |
| Runtime | Evidence collected from the supported disposable Runtime Lab | reconciliation state, workload digest, admission result, recovery result | No |
| Environment | Evidence collected from one explicitly identified supported real non-production environment through authoritative APIs | cloud/cluster identity, real GitOps state, registry/workload identity, DNS/TLS, secret integration, observability, drift/recovery evidence | No |
| Production | Evidence from an explicitly identified production system and execution context | production cluster/runtime, production controls, production incident/recovery evidence | Only when separately scoped and proven |

P0 defines the exact machine-readable representation for the environment tier and its compatibility with existing contracts.

## Scope constraint: one operational lane

v0.3.0 intentionally supports exactly **one real non-production operational cloud/Kubernetes lane**.

P0 MUST select and record by ADR:

- cloud/provider;
- Kubernetes implementation;
- account/subscription/project boundary;
- supported region constraints if relevant;
- registry model;
- identity model;
- remote state model;
- GitOps controller;
- secret integration;
- DNS/TLS integration;
- observability boundary.

The repository may retain multi-cloud reference modules, but v0.3.0 does not require operational AWS/Azure/GCP parity.

## Explicit non-goals

The following are out of scope for the v0.3.0 release gate:

- production validation;
- multi-cloud operational parity;
- multi-tenant organizational federation;
- a general-purpose service catalog;
- organization-wide DORA/product analytics;
- automatic production remediation;
- an AI-generated health verdict that bypasses deterministic evidence;
- an invented aggregate assurance percentage;
- blockchain or distributed-ledger infrastructure for assurance history;
- representing rendered manifests as runtime or environment proof;
- secret material committed to repository fixtures;
- destructive chaos outside an explicit bounded exercise contract.

These can become future releases only after v0.3.0 establishes operational evidence safely.

### Primary deliverables

- environment evidence tier definition;
- supported operational-lane ADR;
- environment identity model;
- trust boundaries across cloud/Kubernetes/GitOps/registry/DNS/TLS/secrets/observability;

- production-denial semantics;
- migration/compatibility rules from v0.2.0;
- threat model;
- executable positive/negative fixtures;
- P1-P6 test matrix.

### Required negative cases

At minimum:

- missing environment identity;
- wrong account/subscription/project;

- Runtime Lab evidence relabeled as environment evidence;
- non-production evidence relabeled as production;
- bootstrap state that cannot be reconciled to declared authority.

### GO condition

P0 passes only when the contracts are executable enough to constrain every later phase and the supported operational lane is frozen by ADR.

## P4 — Bounded Resilience Exercises & Mandatory Re-verification

**Tracking:** #116  
**Blocked by:** #114

P4 proves that current-state assurance changes when the real environment is deliberately degraded.

### Primary deliverables

- allowlisted resilience-exercise contract;
- exact environment safety guard;
- production-target refusal by default;
- reversible mutation/experiment model;
- baseline receipt;
- degraded-state evidence;
- recovery evidence;
- fresh re-verification receipt;
- updated runbooks.

### Minimum scenario set

The exact implementation depends on P0's supported lane, but the release must include at least:

1. workload failure/recovery;
2. GitOps drift/reconciliation;
3. one identity, configuration, certificate, policy, or external-platform dependency failure appropriate to the supported lane.

### Required state progression

```text
VERIFIED
  -> controlled fault
DEGRADED / DRIFT_DETECTED
  -> recovery
RECOVERED
  -> fresh assurance
RECOVERED_AND_REVERIFIED
```

### Required negative cases

At minimum:

- production target;
- wrong environment identity;
- unsupported exercise;
- incomplete cleanup;
- stale recovery evidence;
- failed exercise that attempts to retain historical PASS.

### GO condition

All required scenarios prove detection, bounded recovery, and mandatory fresh re-verification.

## P5 — Tamper-Evident Environment Assurance Ledger

**Tracking:** #117  
**Blocked by:** #115 and #116

P5 turns individual assurance events into a verifiable history.

### Primary deliverables

- versioned ledger schema;
- cryptographic previous-record linkage or equivalently reviewable tamper-evident chain;
- environment identity binding;
- receipt and snapshot/graph identity binding;
- event taxonomy;
- ledger verifier;
- append path;
- export/import or retention semantics;
- machine-readable history;
- human-readable history/reporting.

### Required history semantics

The ledger must be capable of preserving transitions such as:

```text
VERIFIED
DRIFT_DETECTED
DEGRADED
RECOVERY_IN_PROGRESS
RECOVERED
REVERIFIED
```

Historical records remain historical facts. They do not override current assurance state.

### Required negative cases

At minimum:

- record mutation;
- record substitution;
- record reordering;
- broken previous-record digest;
- incompatible environment identity;
- inconsistent receipt identity;
- unsupported schema version.

Truncation detection must be described conservatively according to the retention/storage boundary; GoldenPath must not claim globally immutable history if the backing storage does not prove that property.

### GO condition

A retained chain verifies independently, and controlled mutation of a record or link fails verification.

## Exact-candidate qualification path

P6 must qualify the exact candidate revision rather than a nearby branch state.

Conceptually:

```text
doctor / preflight
  -> repository validation
  -> supply-chain validation
  -> Runtime Lab qualification
  -> real-environment identity verification
  -> independent discovery
  -> observed snapshot
  -> drift evaluation
  -> graph build / explainability checks
  -> environment assurance receipt
  -> required bounded resilience exercises
  -> recovery
  -> fresh re-verification
  -> ledger append
  -> independent receipt + ledger verification
  -> release-candidate evidence bundle
```

Any mismatch between candidate source, desired state, artifact identity, target environment, receipt, graph/snapshot, or ledger record fails the release gate.

## Candidate evidence bundle

The exact filenames are implementation details, but the release must retain machine-readable evidence equivalent to:

- exact candidate/source identity;
- repository validation result;
- Runtime Lab qualification result;
- environment identity;
- observed environment snapshot;
- drift result;
- dependency/identity graph identity;
- environment assurance receipt;
- resilience exercise records;
- post-recovery re-verification receipt;
- ledger/history verification result;
- claim-tier metadata.

The bundle must clearly state that production validation is not claimed.

## Security and secret-handling boundary

No release artifact, fixture, issue, documentation example, or public status page may expose real secret material.

Environment evidence should prefer stable non-secret identifiers and hashes/digests where appropriate. Authentication tokens, private keys, cloud credentials, secret payloads, and other sensitive runtime values are never evidence payloads.

## Failure semantics

The release must preserve at least these classes conceptually:

- verified;
- degraded;
- drift detected;
- recovered but not yet re-verified;
- recovered and re-verified;
- unverifiable;
- infrastructure/tooling failure;
- unsupported target;
- explicitly allowed skip only where a versioned contract permits it.

A tool/API error cannot silently become a platform PASS.

## Compatibility

v0.3.0 must preserve the v0.2.0 evidence boundary and document any schema or CLI migration.

A v0.2.0 runtime receipt does not automatically become v0.3.0 environment evidence. Any new environment claim must be regenerated from the supported authoritative sources and validated under the v0.3.0 contract.

## Maturity target

The release is intended to move GoldenPath from a primarily Level 1 reference baseline toward a demonstrable **Level 2 Operational Paved Road** for one supported real non-production lane.

That maturity movement is justified only by retained operational evidence. It does not imply organization-wide adoption, multi-team scale, or production validation.

## Completion rule

v0.3.0 may be published only when:

- #112 through #118 are complete;
- the exact candidate passes all applicable gates;
- no required evidence is stale or identity-mismatched;
- the real non-production environment is independently observed;
- required drift and recovery exercises are complete;
- fresh post-recovery evidence verifies;
- the ledger verifies;
- public documentation matches the evidence boundary;
- production remains NOT CLAIMED unless a separate future scope proves it.

## Future direction after v0.3.0

Capabilities intentionally deferred include:

- multi-team/platform-product federation;
- service catalog and organizational ownership workflows;
- multi-cluster and multi-cloud operational parity;
- upgrade automation across templates/modules;
- richer cost/FinOps evidence;
- broader compliance evidence automation;
- production qualification.

Those belong to later releases after v0.3.0 establishes a trustworthy operational foundation.

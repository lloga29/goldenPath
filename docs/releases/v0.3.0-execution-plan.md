# GoldenPath v0.3.0 Execution Plan

## Status

**Planned release:** v0.3.0  
**Theme:** Machine-Consumable Assurance & Execution Plane  
**Tracking epic:** #111  
**Execution phases:** P0 through P9  
**Primary integration surface:** CLI + JSON/JSONL + versioned schemas  
**API server:** explicitly deferred; v0.3.0 MUST NOT require a persistent GoldenPath API service  
**Evidence boundary:** GoldenPath proves only the assurance level actually achieved. Local runtime evidence is not cloud assurance, and non-production evidence is not production validation.

GoldenPath v0.3.0 evolves the project from a validated Golden Path implementation into a **machine-consumable Assurance & Execution Plane**.

GoldenPath remains a standalone, public, vendor-neutral, AI-independent open-source project. External systems may consume its documented contracts without depending on GoldenPath internals.

The primary architectural rule is:

```text
Optional Consumer / Automation
"Request execution or assurance"
        |
        | versioned machine-readable contract
        v
GoldenPath
"What is allowed, how is it executed,
and how is it proven?"
        |
        v
Infrastructure / Kubernetes / CI/CD
"Execute the change."
```

GoldenPath MUST NOT contain AI planning logic.

GoldenPath MUST NOT depend on any external orchestrator, controller, CI/CD product, AI system, or private integration.

External orchestrators, CI/CD systems, automation controllers, and human operators MAY consume GoldenPath through the same public contracts.

## Release thesis

GoldenPath v0.1.x established Golden Path foundations.

GoldenPath v0.2.0 established increasingly strong delivery assurance through:

- reproducible Runtime Lab execution;
- runtime evidence;
- continuous assurance;
- signed receipts;
- platform scorecards;
- fail-closed semantics;
- exact-candidate self-qualification.

GoldenPath v0.3.0 makes that assurance **programmable**.

The target progression is:

```text
v0.1.x
Golden Path foundations
        |
        v
v0.2.0
Runtime evidence
Continuous assurance
Signed receipts
Scorecards
Self-qualification
        |
        v
v0.3.0
Machine-readable contracts
Capability-aware execution
Explicit assurance levels
Resumable deterministic execution
Runtime provider abstraction
Certified Changes
External orchestration compatibility
```

The release is complete only when a consumer that knows nothing about GoldenPath internals can discover capabilities, submit a request, observe execution, handle deterministic outcomes, resume when appropriate, retrieve evidence, verify a signed receipt, and determine the assurance level actually achieved.

## Architectural boundary

The standalone/integration boundary is intentional.

| Optional external controller responsibilities | GoldenPath responsibilities |
|---|---|
| Planning | Policies |
| Task decomposition | Execution profiles |
| Agent coordination | Kubernetes validation |
| Prompt construction | Terraform assurance |
| Dependency reasoning | Runtime verification |
| Blast-radius reasoning | Security gates |
| Human-decision workflow | Evidence collection |
| Recovery orchestration | Assurance receipts |
| External execution state | Certification |
| Provider/agent abstraction | Conformance tests |
| AI remediation decisions | Platform scorecards |

The boundary between both systems MUST consist exclusively of documented, versioned contracts.

No GoldenPath package, command, schema, fixture, test, release process, or documentation path may require any external orchestrator/controller.

GoldenPath MUST provide a complete standalone workflow for human developers and CI/CD systems using only its own public CLI, configuration, schemas, and documented contracts.

External integrations are optional adapters/consumers and MUST NOT become required for core execution, assurance, evidence, certification, conformance, or release qualification.

GoldenPath defines facts, allowed operations, execution semantics, evidence, and certification.

An optional external controller may decide intent, planning, sequencing across systems, human workflow, and whether an automatable remediation should be attempted. GoldenPath does not require such a controller to operate.

## Core release invariants

These invariants apply to every phase and may not be weakened for implementation convenience.

1. **Standalone operation remains mandatory.** GoldenPath MUST remain useful without any external orchestrator.
2. **AI independence is mandatory.** GoldenPath MUST NOT require an LLM, prompt, agent runtime, or AI provider to validate, execute, or certify.
3. **Contracts are the integration boundary.** External automation MUST NOT need to parse internal logs or import GoldenPath internals.
4. **Product version and contract version evolve independently.** GoldenPath v0.3.0 may implement `goldenpath.dev/v1`.
5. **Fail closed.** Missing, malformed, stale, contradictory, unsupported, unverifiable, or identity-mismatched required evidence cannot produce certification.
6. **Unknown is not PASS.** Tooling or infrastructure failure must remain explicit.
7. **FAIL and INFRASTRUCTURE_FAILURE are distinct.** Invalid change and inability to determine validity MUST NOT be conflated.
8. **Assurance levels remain truthful.** Local runtime validation cannot be represented as cloud or production-like validation.
9. **Immutable source identity is mandatory.** Branch names alone are insufficient.
10. **Resume must be safe.** GoldenPath MUST NOT blindly repeat destructive actions.
11. **Human approval remains external.** GoldenPath may detect a decision boundary but MUST NOT implement the human approval workflow.
12. **Evidence is minimal and privacy-aware.** GoldenPath MUST NOT persist private prompts, private reasoning, model credentials, provider secrets, internal planning graphs, or unnecessary personal data.
13. **Credentials are referenced, not embedded.** Prefer workload identity, OIDC, ambient CI identity, short-lived credentials, and secret references.
14. **Terraform state ownership remains external to GoldenPath.** GoldenPath governs state policy; it does not become a Terraform backend.
15. **Certified Change is a first-class product concept.** CI success alone is insufficient.
16. **No API server requirement in v0.3.0.** CLI + schemas + JSON/JSONL are the normative integration path.
17. **Simulation is first-class.** External integrations MUST be testable without a cloud account or real Kubernetes target.
18. **Failure injection is first-class.** Machine-readable failure semantics MUST be proven, not merely documented.
19. **Exact-candidate self-qualification remains mandatory.** GoldenPath v0.3.0 MUST qualify GoldenPath v0.3.0.
20. **Continuous assurance compatibility is preserved.** Contracts must not prevent later drift/security/runtime events from being consumed by external controllers.

## Contract versioning model

v0.3.0 introduces a formal contract layer.

A proposed layout is:

```text
contracts/
  v1/
    capability.schema.json
    execution-profile.schema.json
    execution-request.schema.json
    execution-result.schema.json
    execution-event.schema.json
    evidence.schema.json
    assurance-receipt.schema.json
    policy-result.schema.json
```

Equivalent YAML representations SHOULD be supported where practical, but JSON Schema is normative for validation.

Example:

```yaml
apiVersion: goldenpath.dev/v1
kind: ExecutionRequest
```

GoldenPath release version and contract API version MUST evolve independently.

Backward-compatible changes may remain in `goldenpath.dev/v1`.

Breaking contract changes require a new contract API version and explicit migration/conformance coverage.

## Capability discovery

An external controller must be able to determine what the current execution environment can actually do before constructing an execution plan.

Normative command:

```text
goldenpath capabilities --format json
```

Conceptual result:

```yaml
apiVersion: goldenpath.dev/v1
kind: CapabilityReport

runtime:
  docker: true
  kubernetes:
    local: true
    provider: kind

iac:
  terraform:
    installed: true
    validate: true
    test: true
    plan: false
    apply: false

cloud:
  azure: false
  aws: false
  gcp: false

security:
  policyEngine: true
  imageScanning: true
  signing: true

evidence:
  collection: true
  signedReceipts: true
```

Capabilities MUST reflect the real environment, not theoretical GoldenPath features.

Capability discovery SHOULD distinguish:

- binary installed;
- feature supported;
- feature configured;
- credentials/identity available;
- target reachable;
- operation authorized.

An unavailable capability must never be silently treated as success.

## Execution profiles

GoldenPath MUST support explicit execution profiles.

| Profile | Runtime | Intended use |
|---|---|---|
| `static` | none | Fast source, IaC, security, schema, and policy validation |
| `local-runtime` | kind/k3d or equivalent | Ephemeral Kubernetes runtime validation |
| `cloud-sandbox` | AKS/EKS/GKE or equivalent | Cloud-specific integration validation |
| `production-like` | staging/pre-production | Release qualification under production-like controls |
| `production-observe` | existing production | Read-only/explicitly bounded evidence and continuous assurance |

Profiles describe required capabilities and assurance intent, not merely environment names.

Conceptual profile:

```yaml
apiVersion: goldenpath.dev/v1
kind: ExecutionProfile

metadata:
  name: local-runtime

runtime:
  kubernetes:
    required: true
    ephemeral: true

terraform:
  validate: true
  apply: false

cloud:
  required: false

evidence:
  required: true
```

A profile MUST define allowed/forbidden operation classes, evidence requirements, capability requirements, and cleanup expectations.

Production-observe MUST default to non-mutating behavior unless a separate explicit future contract authorizes otherwise.

## Assurance levels

GoldenPath SHOULD formalize explicit assurance levels.

| Level | Meaning |
|---|---|
| L0 | Static assurance |
| L1 | Local runtime assurance |
| L2 | Cloud sandbox assurance |
| L3 | Production-like assurance |
| L4 | Production runtime evidence |

Every run MUST state both requested and achieved assurance.

Example:

```yaml
assurance:
  requested: L3
  achieved: L1

verified:
  source: PASS
  policy: PASS
  kubernetesRuntime: PASS
  healthChecks: PASS

deferred:
  cloudIdentity: true
  cloudLoadBalancer: true
  managedKMS: true
```

Assurance level is not a numeric quality score.

An achieved level means the documented requirements for that level were actually proven.

If requested assurance cannot be achieved because capabilities are missing, the result MUST state the achieved level and why the requested level was not reached.

Local Kubernetes validation MUST never be represented as cloud assurance.

GoldenPath MUST expose a deterministic lifecycle independent of runtime provider.

Normative conceptual lifecycle:

```text

   v
VALIDATE
   |
   v

   v

   |
   v
VERIFY
   |
```

The lifecycle MUST survive interruption between phases.

## Normalized run states

GoldenPath MUST stop relying on ambiguous textual success/failure messages.

Required normalized states:

```text
PENDING
RUNNING

PASS
FAIL

NEEDS_HUMAN
DEFERRED
NOT_APPLICABLE

INFRASTRUCTURE_FAILURE
CONTRACT_ERROR

CANCELLED
```

Semantics:

- `PASS`: the required validation/execution condition succeeded.
- `FAIL`: the subject being validated violates the contract or policy.
- `NEEDS_HUMAN`: execution reached a defined human-decision boundary.
- `DEFERRED`: an optional or higher-assurance gate cannot execute because a declared capability is unavailable.
- `NOT_APPLICABLE`: the gate is validly outside the current request/profile.
- `INFRASTRUCTURE_FAILURE`: GoldenPath could not reliably determine validity because the execution infrastructure/tooling failed.
- `CONTRACT_ERROR`: the request, schema, version, or semantic contract is invalid.
- `CANCELLED`: the run was intentionally terminated.

A `FAIL` MUST NOT be rewritten as `INFRASTRUCTURE_FAILURE`, and vice versa.

## Human decision boundary

GoldenPath MAY detect that execution requires explicit human authorization.

GoldenPath MUST NOT own the approval workflow.

Conceptual result:

```yaml
status: NEEDS_HUMAN

decision:
  id: decision-789
  reason: PRODUCTION_APPLY_REQUIRED
  options:
    - approve
    - reject
```

An external controller is responsible for:

```text
pause
  |
  v
obtain human decision
  |
  v
persist decision
  |
  v
resume GoldenPath execution
```

GoldenPath MUST validate that a supplied decision references the correct run, decision ID, immutable source identity, and currently pending decision.

## Resume and idempotency

External automation compatibility requires safe resumption.

Every execution SHOULD persist or reconstruct at least:

- request ID;
- GoldenPath run ID;
- change ID;
- repository identity;
- base revision;
- exact revision;
- execution profile;
- requested/achieved assurance;
- policy bundle digest;
- current execution phase;
- completed gates;
- pending gates;
- evidence root/digest;
- runtime provider identity/version;
- GoldenPath version;
- contract version.

Normative command:

```text
goldenpath resume --run-id gp_run_123
```

Operations MUST be classified as one of:

- `safe-to-repeat`
- `state-aware`
- `non-repeatable`
- `approval-required`

Resume MUST NOT blindly re-run completed destructive operations.

State-aware resume MUST compare persisted identity and current target state before deciding whether an action can continue.

Identity mismatch during resume MUST fail closed.

## Stable exit codes

The CLI SHOULD expose stable exit-code categories.

Initial contract:

| Exit code | Meaning |
|---:|---|
| 0 | completed successfully |
| 10 | validation or policy failure |
| 20 | human decision required |
| 30 | capability unavailable / deferred |
| 40 | infrastructure failure |
| 50 | invalid contract/request |
| 60 | GoldenPath internal failure |

The JSON result is authoritative.

Exit codes are a first-level integration mechanism and MUST remain documented and covered by conformance tests.

If future states require expansion, backward compatibility must be preserved or versioned.

## Terraform integration model

GoldenPath MUST NOT become the owner or storage backend of Terraform state.

GoldenPath governs **state policy**.

For shared/cloud environments GoldenPath SHOULD validate controls such as:

- remote backend usage;
- locking or equivalent concurrency protection;
- encryption;
- environment isolation;
- backend access control;
- no long-lived credentials embedded in backend configuration;
- backend-policy compliance;
- environment/account identity consistency.

For isolated ephemeral Runtime Lab executions, temporary local state MAY be permitted where appropriate.

Conceptual policy:

```yaml
terraform:
  state:
    mode: ephemeral
    lifecycle: execution
    cleanupRequired: true
```

Shared/staging/production-like example:

```yaml
terraform:
  state:
    mode: remote
    lockingRequired: true
    encryptionRequired: true
```

GoldenPath validates and proves state-management policy. It does not replace Terraform's backend.

## Terraform capability awareness

GoldenPath MUST distinguish at least:

Static/offline-friendly operations:

- `terraform fmt`
- `terraform validate`
- `terraform test` where supported by the module/test
- `tflint`
- Checkov
- policy validation

Potentially environment-dependent operations:

- `terraform init`
- `terraform plan`
- provider/data-source evaluation

Environment-mutating operations:

- `terraform apply`

`plan` MUST NOT be assumed to be offline. It may require provider initialization, credentials, remote state, external data, or reachable services.

`apply` requires a real target and explicit authorization semantics.

Terraform gates MUST advertise required capabilities and fail/defer according to the contract.

## Ephemeral Kubernetes Runtime Lab

`local-runtime` becomes a first-class execution target.

Expected lifecycle:

```text
runner
  |
  v
create ephemeral kind/k3d cluster
  |
  v
bootstrap required components
  |
  v
deploy candidate
  |
  v
run runtime validation
  |
  v
collect logs/events/metrics/results
  |
  v
produce evidence
  |
  v
destroy runtime
```

The Runtime Lab MUST be disposable and reproducible.

Evidence MUST be produced before destructive cleanup removes the environment.

The result MUST explicitly identify the runtime as local/ephemeral.

Runtime Lab PASS cannot satisfy a cloud-specific assurance requirement.

## Cloud-specific gates

Cloud-dependent gates MUST declare required capabilities.

Conceptual example:

```yaml
gate:
  name: azure-workload-identity

requires:
  cloud: azure
  kubernetes: true
  oidc: true
```

When the required capability is unavailable:

```yaml
status: DEFERRED
reason: CAPABILITY_UNAVAILABLE
```

A run may still achieve a lower assurance level when the profile allows it.

GoldenPath MUST prevent certification at an assurance level whose required gates were not actually satisfied.

## Policy-as-code result contract

Policy decisions SHOULD return structured results.

Conceptual example:

```yaml
gate: container-security
status: FAIL

policy:
  id: GP-SEC-014
  version: 3

evidence:
  digest: sha256:...

remediation:
  automatable: true
  category: CONFIGURATION
  message: Container must define a non-root user.
```

`automatable` is metadata, not an instruction for GoldenPath to perform AI remediation.

GoldenPath provides the deterministic fact.

An optional external consumer may decide whether to attempt remediation, require a human, or terminate. GoldenPath remains fully usable without that consumer.

## Evidence contract

Evidence from every gate SHOULD use one common envelope.

Conceptual example:

```yaml
apiVersion: goldenpath.dev/v1
kind: Evidence

runId: gp_run_123

subject:
  repository: example/payments
  revision: def456

gate:
  id: GP-K8S-RUNTIME

  profile: local-runtime
  runtime: kind

artifacts:
  - type: kubernetes-events
    digest: sha256:...
  - type: test-results
    digest: sha256:...

timestamp: ...
```

Evidence MUST be immutable once incorporated into a signed assurance receipt.

Evidence payloads SHOULD contain digests/references rather than secrets or unnecessarily large raw data when possible.

Canonicalization rules for digested/signed evidence MUST be deterministic and documented.

## Certified Change

v0.3.0 introduces **Certified Change** as a central product concept.

A change is not certified merely because CI is green.

A Certified Change binds:

```text
source revision
      +
execution environment
      +
policy version
      +
gate results
      +
runtime evidence
      +
assurance level
      +
signed assurance receipt
      =
CERTIFIED CHANGE
```

The certification identity MUST be reproducibly derived or referenced from immutable inputs.

Any external verifier or automation consumer should be able to ask:

> What assurance level did this exact change achieve, and where is the cryptographically bound evidence?

rather than:

> Did the pipeline pass?

## Evidence privacy boundary

GoldenPath is public and may be consumed by private systems.

GoldenPath receipts and evidence MUST NOT automatically persist:

- agent prompts;
- model chain-of-thought/private reasoning;
- model credentials;
- provider credentials;
- private planning graphs;
- repository secrets;
- raw long-lived tokens;
- unnecessary human personal data.

GoldenPath records only the minimum information needed to prove what was validated, executed, and certified.

Secret material SHOULD be represented by identity/secret references where needed, never embedded as evidence.

---

## Identity and credentials

External systems SHOULD pass execution context without transporting raw long-lived credentials inside GoldenPath contracts.

Preferred mechanisms:

- OIDC;
- workload identity;
- ambient CI identity;
- short-lived credentials;
- secret references.

Conceptual example:

```yaml
credentials:
  mode: workload-identity
  reference: github-actions
```

Forbidden pattern:

```yaml
credentials:
  azureSecret: actual-secret-value
```

Schemas, examples, tests, and fixtures MUST NOT normalize secret embedding as the expected integration pattern.

## Immutable execution identity

Every run MUST bind to immutable source/execution identity.

At minimum, where applicable:

- repository;
- exact commit SHA;
- policy bundle digest;
- GoldenPath version;
- contract version;
- execution profile;
- runtime provider;
- runtime provider version;
- target environment identity when used;
- artifact digest where produced/validated.

Branches/tags alone are insufficient because they can move or be recreated.

## Simulated provider

A deterministic simulation provider is a v0.3.0 release requirement.

Normative conceptual invocation:

```text
goldenpath run request.yaml --provider simulated
```

The provider MUST be able to generate controlled scenarios including:

- PASS;
- FAIL;
- NEEDS_HUMAN;
- INFRASTRUCTURE_FAILURE;
- DEFERRED.

The simulation provider MUST use the same public result/event contracts as real providers.

It MUST NOT be a separate mock-only data shape that allows integration tests to bypass the production contract.

The simulated provider enables development and recovery testing for any external consumer without requiring a Kubernetes cluster or cloud account.

## Failure injection

Runtime and simulation testing MUST support controlled failures.

Minimum scenarios:

- pod never becomes ready;
- image pull failure;
- policy rejection;
- Terraform validation failure;
- cluster unavailable;
- evidence collection failure;
- cleanup failure;
- human decision required.

Every scenario MUST prove the expected machine-readable state, exit code, events, and certification behavior.

Where a failure occurs after some evidence has been produced, the final result MUST preserve the distinction between completed facts and incomplete certification.

## Fail-closed certification

GoldenPath's existing fail-closed philosophy remains mandatory.

Examples:

```text
Gate PASS
+
Evidence collection failed
=
NOT CERTIFIED
```

```text
All local-runtime gates PASS
+
L3 requested
+
cloud gates unavailable
=
L1 achieved
L3 NOT CERTIFIED
```

Required evidence cannot be replaced by a textual success message.

A cleanup failure MAY occur after certification inputs have been collected, but the run result MUST still report cleanup failure explicitly and the certification policy MUST define whether that profile permits certification under that condition.

- drift detected;
- policy changed;
- runtime evidence expired;
- security posture changed;
- deployment changed;
- infrastructure changed.

GoldenPath remains the detector and evidence authority.

GoldenPath remains the detector and evidence authority. Optional external automation may consume those facts and decide whether any follow-up action is appropriate.

v0.3.0 does not require a permanent streaming service; compatibility at the contract/event level is sufficient.

Rationale:

- P0 freezes the architectural boundary before implementation.
- P1 freezes the public data contracts.
- P2 defines capability/profile/assurance semantics consumed by execution.
- P3 defines deterministic lifecycle/state/events before provider implementations are generalized.
- P4 and P5 may proceed in parallel once P3 exists.
- P6 depends on runtime/IaC facts because certification must bind real normalized evidence.
- P7 depends on the complete executable/certification surface.
- P8 proves interoperability and failures deterministically.
- P9 qualifies the exact release candidate.

No phase may weaken a contract defined by an earlier completed phase without reopening and requalifying the affected dependency chain.

- persistent API server explicitly deferred;
- product/contract version independence;
- human-decision boundary;
- evidence/privacy boundary;
- credential boundary;
- assurance-level truthfulness;
- Terraform state ownership boundary;
- compatibility expectations from v0.2.0.

### Required deliverables

- architecture ADR;
- public/private responsibility matrix;
- trust-boundary diagram;
- contract versioning ADR/rules;
- v0.2.0 compatibility/migration notes;
- threat model update;
- P1-P9 test matrix.

### GO condition

No implementation proceeds under a model where GoldenPath plans with AI, owns external orchestration state, owns Terraform remote state, or requires a permanent API server.

## Release gate

v0.3.0 MUST NOT be published unless:

1. P0-P9 acceptance gates are complete.
2. Required v1 contracts validate and pass compatibility tests.
3. Capability discovery reflects the actual runner/environment.
4. Execution profiles and L0-L4 semantics are enforced.
5. Deterministic state, exit-code, event, and resume semantics pass.
6. `kind`, `existing-kubernetes`, and `simulated` provider contracts pass their required tests.
7. Terraform state-policy behavior is proven without GoldenPath owning state.
8. Evidence and Assurance Receipt v2 verification pass.
9. Certified Change binds the exact candidate revision and assurance level.
10. Required failure-injection scenarios produce the documented states.
11. Fail-closed certification rejects incomplete required evidence.
12. The exact release candidate passes self-qualification.
13. Documentation accurately separates local, cloud, production-like, and production evidence.
14. No mandatory release check depends on any external controller, orchestrator, proprietary integration, or unavailable private infrastructure.
15. The release tag points to the exact qualified commit.

## Explicit non-goals for v0.3.0

The following are intentionally out of scope:

- a permanent GoldenPath API server;
- REST/gRPC as a required integration transport;
- AI planning inside GoldenPath;
- vendor-, product-, or controller-specific integration code inside GoldenPath core;
- GoldenPath-owned human approval workflow;
- GoldenPath-owned Terraform remote state service;
- mandatory AKS/EKS/GKE availability for the release;
- multi-cloud operational parity;
- production mutation/remediation;
- automatic AI remediation;
- production certification without explicit production evidence;
- organization-wide service catalog/federation;
- hidden credential transport in execution contracts.

These may evolve in later releases after the v1 public contract proves stable.

```text

   v
GoldenPath

   |
```

GoldenPath becomes the public deterministic authority for what is allowed, what was executed, what evidence exists, and what assurance level was achieved.

Any external controller may evolve independently and consume GoldenPath through the same stable public contracts.

GoldenPath remains complete and fully usable without any external controller. Integrations are optional consumers of the platform, not architectural dependencies.

# GoldenPath v0.2.0 Execution Plan

## Status

**Planned release:** v0.2.0  
**Theme:** Runtime Evidence & Autonomous Assurance  
**Tracking epic:** #91  
**Execution phases:** #92 through #97  
**Evidence boundary:** repository/reference evidence and ephemeral-runtime evidence only unless a separate real-system validation scope is explicitly introduced.

GoldenPath v0.2.0 is not a claim of infallibility or production certification. Its goal is to make failures safer, detectable, diagnosable, recoverable, and provable through evidence.

## Release thesis

GoldenPath v0.1.0 established a public repository/reference baseline with deterministic risk-adaptive assurance, fail-closed evidence semantics, policy as code, immutable promotion, SBOM/SLSA/Cosign controls, and explicit separation between repository, runtime, and production claims.

v0.2.0 moves the project one level higher:

```text
Intent
  -> Risk
  -> Assurance Plan
  -> Build
  -> Attestation
  -> GitOps Promotion
  -> Runtime Reconciliation
  -> Observation
  -> Verification
  -> Assurance Receipt
  -> Recovery / Re-verification
```

The release must prove that GoldenPath can execute this chain in a reproducible isolated Kubernetes runtime while binding the evidence to exact identities.

## Core release invariants

These constraints apply to every phase and may not be weakened by implementation convenience.

1. **Fail closed.** Missing, malformed, stale, contradictory, unsupported, or identity-mismatched required evidence must not produce a passing assurance result.
2. **Evidence tiers stay distinct.** Repository/reference evidence, runtime evidence, and production validation are separate claim classes.
3. **No production claim from the lab.** An ephemeral local or CI cluster is runtime evidence, not production validation.
4. **Identity binding is mandatory.** Evidence must bind to the exact source revision, artifact digest, desired-state revision, applicable policy/assurance plan, and runtime identity where relevant.
5. **Immutable artifacts remain authoritative.** Build once and promote by digest.
6. **GitOps remains the desired-state authority.** The lab may require documented bootstrap actions, but hidden or untracked mutation must not become the steady-state model.
7. **Positive evidence is insufficient by itself.** Every security- or assurance-relevant contract requires negative/adversarial tests.
8. **Historical PASS does not override current failure.** Continuous assurance must distinguish previous receipts from current state.
9. **Human boundaries remain explicit.** Automation must not silently cross approval or production-control boundaries.
10. **GoldenPath must qualify GoldenPath.** The exact v0.2.0 release candidate must run through the same assurance model used by the release.

## Evidence model

v0.2.0 introduces a practical three-tier claim model:

| Tier | Meaning | Example evidence | May claim production? |
|---|---|---|---|
| Repository/reference | Static, generated, fixture, CI, policy, architecture, or desired-state evidence | schema validation, policy tests, signed provenance verification | No |
| Runtime | Evidence collected from a real Kubernetes API/runtime in the supported Runtime Lab | reconciliation state, workload digest, admission result, health, recovery result | No |
| Production | Evidence from an explicitly identified real production system and execution context | real cluster/runtime, real operational controls, real incident/recovery evidence | Only when separately scoped and proven |

The default v0.2.0 release target is the first two tiers.

## Phase sequence

### P0 — Architecture & Assurance Contracts

**Tracking:** #92

P0 defines the contracts before implementation expands.

Primary deliverables:

- runtime evidence trust model;
- versioned runtime evidence schema;
- versioned assurance receipt schema;
- identity-binding rules;
- freshness/replay/tamper semantics;
- evidence-tier claim rules;
- Runtime Lab architecture and isolation assumptions;
- CLI architecture and command-contract draft;
- threat model;
- compatibility and migration notes;
- ADRs for durable decisions.

Required negative cases include missing identities, mismatched artifact/source/desired-state identities, stale evidence, unsupported schema versions, contradictory outcomes, and attempts to promote lab evidence to production claims.

**GO condition:** schemas, ADRs, threat model, fixtures, and rejection semantics are accepted and executable enough to constrain P1-P5.

---

### P1 — Reproducible Runtime Lab

**Tracking:** #93

P1 creates a disposable Kubernetes runtime that exercises the GoldenPath contracts against a real Kubernetes API.

Primary deliverables:

- supported ephemeral Kubernetes engine and lifecycle;
- deterministic create/bootstrap/destroy path;
- CI-compatible smoke execution;
- supported platform subset;
- Argo CD reconciliation path or explicitly documented bootstrap boundary;
- generated reference workload;
- policy admission positive/negative tests;
- runtime workload identity verification by immutable digest;
- cleanup and residue checks.

Minimum successful path:

1. create the lab;
2. bootstrap the supported platform subset;
3. reconcile the reference workload;
4. prove at least one policy denial;
5. capture runtime health facts;
6. destroy the environment and verify expected cleanup.

**GO condition:** a clean environment can reproduce the full lifecycle without using rendered manifests as a substitute for runtime evidence.

---

### P2 — Runtime Evidence & Signed Assurance Receipts

**Tracking:** #94

P2 converts runtime facts into independently verifiable evidence.

Primary deliverables:

- runtime evidence collectors;
- source -> artifact -> desired state -> runtime identity binding;
- applicable assurance/policy-plan binding;
- deterministic receipt generation;
- independent receipt validation;
- cryptographic signing and verification;
- tamper/replay/staleness/mismatch rejection;
- machine-readable and human-readable evidence views.

A receipt must be capable of representing, at minimum:

```yaml
source:
  revision: <exact commit>

artifact:
  imageDigest: sha256:...

gitops:
  desiredStateRevision: <exact commit>

policy:
  assurancePlan: <identity>
  policyBundle: <identity>

runtime:
  clusterIdentity: <bounded runtime identity>
  workloadIdentity: <observed digest/revision>

controls:
  signatureVerification: PASS
  provenanceVerification: PASS
  admissionPolicy: PASS
  runtimeHealth: PASS

claim:
  tier: runtime
```

**GO condition:** a valid Runtime Lab execution produces a receipt that verifies independently, while controlled mutation of any required identity or signature fails closed.

---

### P3 — Resilience, Drift & Continuous Assurance

**Tracking:** #95

P3 ensures a successful deployment is not treated as permanent proof of health.

Primary deliverables:

- selected continuous-assurance checks;
- GitOps/runtime drift detection;
- controlled rollback exercise;
- policy-denial and bypass-attempt scenarios;
- expired/invalid exception behavior where applicable;
- failure injection with bounded blast radius;
- recovery evidence;
- current-state vs historical-receipt semantics;
- updated runbooks.

Required outcome classes must include:

- verified healthy;
- detected degraded;
- recovered and re-verified;
- failed;
- needs-human where automation cannot safely resolve the condition.

**GO condition:** controlled failures are detected and cannot retain a false passing state; recovery produces new evidence rather than rewriting history.

---

### P4 — GoldenPath CLI, Reports & Scorecards

**Tracking:** #96

P4 turns the underlying mechanics into a coherent paved-road experience.

Candidate command surface:

```text
goldenpath init
goldenpath plan
goldenpath validate
goldenpath lab up
goldenpath lab down
goldenpath assure
goldenpath verify
goldenpath doctor
goldenpath evidence show
```

The exact command set may be refined by P0, but the following properties are mandatory:

- machine-readable output for automation;
- human-readable output for operators;
- explicit dependency diagnostics;
- no hidden downgrade from fail-closed to advisory behavior;
- evidence-tier labels in reports;
- actionable failure causes;
- no invented scorecard metrics.

Target report shape:

```text
GoldenPath Assurance Report

Risk Level                R3
Source Integrity          PASS
IaC / Policy              PASS
Supply Chain              PASS
SBOM                      PASS
SLSA Provenance           PASS
Signature                 PASS
GitOps Integrity          PASS
Admission Control         PASS
Runtime Health            PASS
Recovery                  PASS
Drift                     PASS

Repository Evidence       VERIFIED
Runtime Evidence          VERIFIED
Production Validation     NOT CLAIMED
```

**GO condition:** a user can traverse the supported v0.2.0 assurance path through the official entry point and receive evidence equivalent to the lower-level implementation.

### P5 — Self-Qualification, Hardening & Release

**Tracking:** #97

P5 qualifies the exact release candidate.

Primary deliverables:

- complete repository/reference validation;
- complete supported Runtime Lab validation;
- exact release-candidate assurance receipt;
- adversarial/negative test pass;
- release SBOM/provenance/signing evidence where technically applicable;
- updated architecture, quickstart, demo, showcase, changelog, migration notes, and release runbook;
- public documentation claim review;
- post-release verification checklist.

v0.2.0 MUST NOT be published when:

- any P0-P5 acceptance gate is incomplete;
- required evidence is missing, stale, mismatched, malformed, or unverifiable;
- required tests are red;
- required tests are silently skipped outside an explicitly allowed contract;
- the release receipt fails verification;
- documentation implies production validation unsupported by evidence.

**GO condition:** the exact candidate self-qualifies using the v0.2.0 assurance path and all release documentation matches the evidence boundary.

## Execution discipline

### Branches and pull requests

- Use conventional descriptive branch names such as `feat/...`, `fix/...`, `docs/...`, `chore/...`, or `refactor/...`.
- Keep changes small, auditable, and reversible.
- Prefer one logical change per PR.
- Do not merge while relevant checks for the exact PR head are incomplete or failing.
- Revalidate that `main` has not advanced incompatibly before merge.
- Preserve the repository's authoring and no-AI-trailer conventions.

### Phase completion

A phase is not complete because code exists. It is complete only when:

1. its required deliverables exist;
2. its positive path passes;
3. its required negative paths pass;
4. evidence is captured at the correct tier;
5. documentation matches implementation;
6. the phase issue's acceptance gate is satisfied.

### Cross-phase dependencies

Parallel prototypes are allowed, but no later phase may be declared complete before its dependency gate is satisfied.

## Non-goals for v0.2.0

Unless separately approved, v0.2.0 does not require:

- claiming production readiness for a real organization;
- validating every Kubernetes distribution;
- validating every cloud provider runtime;
- replacing Argo CD;
- building a full commercial internal developer portal;
- hiding Terraform, Kubernetes, policy, or supply-chain tools behind opaque automation;
- eliminating all human decision points;
- certifying compliance with an external regulatory or security framework.

Compliance mappings may be informational and evidence-backed, but must not be described as certifications.

## Candidate follow-on releases

The v0.2.0 architecture should leave room for:

- **v0.3.0:** self-service developer platform and broader template/catalog experience;
- **v0.4.0:** multi-cluster and multi-cloud runtime assurance;
- **v0.5.0:** continuous compliance, recovery, and fleet-level assurance;
- **v1.0.0:** explicit compatibility and production-adoption contract.

These are directional only and do not weaken the acceptance criteria for v0.2.0.

## Definition of release success

GoldenPath v0.2.0 succeeds when an independent reviewer can take the exact release candidate and determine, from reproducible execution and verifiable evidence, that:

- repository/reference controls passed;
- the supported Runtime Lab actually ran;
- the exact artifact and desired state were observed in that runtime;
- required admission and runtime controls behaved as defined;
- selected failure/recovery scenarios were exercised;
- the resulting assurance receipt is valid and identity-bound;
- negative tamper/mismatch cases fail closed;
- and no unsupported production claim is made.

That is the v0.2.0 release contract.
